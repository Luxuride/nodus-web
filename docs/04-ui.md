# 04 — UI

Status: draft · Last revised: 2026-11-06

Tailwind 4 with daisyUI 5, compiled by the Tailwind standalone CLI (no Node, no
npm). The component vocabulary is daisyUI's (`card`, `btn`, `alert`, `menu`,
`badge`, `input`), so a view reads as markup and a designer can change a component
by changing a class rather than hunting a rule.

Why not hand-written CSS: the styling layer must stay boring, and "boring" is
cheaper to keep when the components are somebody else's maintained defaults than
when they are a 300-line stylesheet that drifts per screen. Why Tailwind at all
instead of only daisyUI: daisyUI has no layout, and layout utilities are what keep
`main.rs` readable without a stylesheet.

Both are pinned and vendored rather than fetched at build time — the plugin lives
in `vendor/daisyUI` (see `vendor/VENDOR.md`) and Tailwind's version is pinned in
`.devcontainer/post-create.sh`, because a Tailwind minor can change which utilities
exist and nothing reviews generated CSS.

Division of labour, and the rule that keeps it from rotting:

- `style/theme.css` holds **tokens only**: fonts, radius, accent, and the oklch
  values behind daisyUI's semantic colours (`--color-base-100`, `--color-primary`,
  …) for the `light` and `dark` themes.
- `style/app.css` is the entry point: Tailwind, then the daisyUI plugin, then our
tokens, then `@source "../src/**/*.rs"` — Tailwind scans the views, so unused
components cost nothing.
- **No component rules of our own.** If a screen needs one, it is a missing token
  or a missing daisyUI pattern; adding the rule is the point at which the design
  system stops being one.

## Rendering untrusted content

Statuses, bios and display names are HTML produced by a third-party instance.
They are treated as hostile input:

- **Sanitize once, at parse time**, in a single `ui/sanitize.rs` with an
  allow-list: `p, br, a, span, del, code, pre, blockquote, ul, ol, li, strong,
  em, h1..h4, ruby, rt, rp`. Attributes: `href` (only `http(s)` and `mailto`),
  `class` (from a known set), `rel`, `title`, `lang`. No `style`, no `on*`, no
  `iframe`, no `svg`.
- **Links** get `rel="nofollow noopener noreferrer"` and `target="_blank"`; the
  sanitizer rejects `javascript:` and `data:` URLs.
- **Plain text** (profile fields, alt text, reasons from our API) is rendered as
  text nodes, never through the HTML path. There is exactly one
  `inner_html`-equivalent call in the codebase and it is fed sanitizer output.
- **Custom emoji** are resolved against the instance's emoji list into `<img>`
  with `alt=":shortcode:"`, `loading="lazy"`, fixed line-height boxes to avoid
  reflow.
- **Media** is never proxied: `<img>`/`<video>` point at the instance, with
  `referrerpolicy="no-referrer"`, `loading="lazy"`, a solid placeholder box of
  the known aspect ratio, and `alt` surfaced (badge "ALT" when present).

A unit test asserts that a battery of XSS payloads renders inert; it runs in CI
(`wasm-bindgen-test`).

## Lists and performance

- **Virtualization**: timelines render a windowed list with estimated heights,
  corrected on mount via `ResizeObserver`. Nothing off-screen is mounted; media
  below the fold is not fetched.
- **Keys**: every status list is keyed by status id, so a stream prepend does not
  remount the visible window.
- **Scroll restoration**: from the cache entry's scroll offset, so back
  navigation lands where the user left.
- **Streaming inserts** never jump the viewport: while the user is scrolled away
  from the top, new items accumulate behind a "N new posts" button.
- **Skeletons** match the final layout to avoid layout shift; the shell paints
  before any data arrives.

## Shell and navigation

```text
┌──────────────────────────────────────────────────────────────┐
│ sidebar rail          │ timeline column    │ context column   │
│  Feed ●               │  (virtualized)     │  (thread detail, │
│  Home                 │                    │   profile, feed  │
│  Local / Federated    │                    │   detail)        │
│  Notifications        │                    │                  │
│  Search · Lists       │                    │                  │
│  Bookmarks · Favourites│                   │                  │
│  [compose]            │                    │                  │
│  avatar · settings    │                    │                  │
└──────────────────────────────────────────────────────────────┘
```

- Three columns on desktop, one column + bottom nav on mobile, rail collapses to
  icons under 1100 px.
- The compose box is a modal on desktop, a full-screen route on mobile; the same
  component in both cases.
- Feed items are cards with an avatar, name, handle, a one-line reason chip
  ("followed by 3 people you follow", "popular on your instance"), a follow
  button with optimistic state, and a dismiss control. Reason text comes from the
  API — the client does not compose reasons from raw numbers.

## Theming and motion

- daisyUI's semantic colours are the source; `style/theme.css` overrides their
  oklch values per theme and adds fonts, radius and the accent alias. Views never
  use raw colours, only semantic roles (`bg-base-100`, `text-error`).
- `color-scheme: light dark` with daisyUI's `light`/`dark` themes as the pair; a
  user override is a `data-theme` attribute, which is the mechanism daisyUI
  already uses, so there is no second theming path.
- Optional per-instance accent colour (the instance's `thumbnail` hue), opt-in.
- Focus rings are visible in every theme; no `outline: none` without a
  replacement.
- Motion is limited to route transitions, dialogs and toasts, and respects
  `prefers-reduced-motion`. No parallax, no autoplay video.

## Accessibility

Non-negotiable and cheaper continuous than retrofitted:

- Semantic landmarks (`main`, `nav`, `article` per status), real `<button>`/`<a>`,
  labelled toolbars for status actions.
- Streaming inserts and toasts announce via a polite `aria-live` region; the
  "N new posts" button is focusable and does not steal focus.
- Keyboard-first: `j/k` move, `enter` opens, `r` reply, `b` boost, `f` favourite,
  `n` notifications, `g`-prefix navigation (`g h`, `g l`, `g f`, `g n`), `?`
  opens the shortcut reference; `esc` closes dialogs and returns focus to the
  invoking element.
- Every image has required alt text surfaced for screen readers; decorative
  avatars are `alt=""`.
- Contrast checked per theme (WCAG AA target); no state conveyed by colour alone
  (the Feed's reason chips carry text, not just a colour).
- Verification: axe smoke tests on key routes in Playwright, plus a manual
  VoiceOver/NVDA pass each milestone (recorded in the milestone PR).

## Internationalization

- `leptos_i18n` with Fluent `.ftl` bundles in `crates/web/locales/`; English is
  the source and the only bundle in the first release.
- No concatenated strings: plurals, gender, and "followed by N people" go through
  Fluent selectors.
- Dates, times, relative ages and numbers via `Intl` from `js-sys`, so CLDR data
  is not reimplemented in wasm.
- Direction (`dir="rtl"`) support is kept in the CSS from day one (logical
  properties: `margin-inline-start`, not `margin-left`), because retrofitting is
  a rewrite.

## Empty, loading and error states

Every view has all four states designed, not just the happy one:

| State | Rule |
| --- | --- |
| Loading (cold) | skeleton matching final layout |
| Loading (warm) | cached content + subtle refresh indicator |
| Empty | explains *why* it is empty and what to do next (e.g. feed: "Follow a few accounts so we can find people like them") |
| Error | inline card with retry and a plain-language cause; the rest of the app stays usable |

The Feed tab additionally renders **degraded** states from the API
(`cold_start`, `stale_similarity`, `no_server_sync`) as a single line of text
above the list, because a recommender that hides its own uncertainty is worse
than one that says "these will improve after your first sync".
